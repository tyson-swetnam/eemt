# Software bills of materials (SBOMs)

This directory holds the generated SBOMs of EEMT: what is inside the container images,
the locked environments and the rsun Rust workspace. Every file here except this README
is generated by `scripts/sbom/generate.sh`. Do not edit them by hand.

Each target has two files:

- `<name>.cdx.json` in CycloneDX 1.7 JSON
- `<name>.spdx.json` in SPDX 2.3 JSON

The generated files are under CC0-1.0 (see `REUSE.toml`). SPDX 2.3 requires this
licence for its documents.

## Files

| Target | Kind | Described from | What it lists |
|---|---|---|---|
| `eemt` | aggregate | the documents below | The release (`docker/VERSION`), with one entry per member document. Members are nested: each image contains the environment installed in it. CycloneDX members point to their document by BOM-Link (`urn:cdx:<serial>/1`) with its SHA-256. SPDX members use `externalDocumentRefs` with the SHA-1 that SPDX 2.3 requires. |
| `image-eemt` | image | `eemt:<VERSION>` (`docker/workflow/Dockerfile`), scanned by syft | Ubuntu 26.04 deb packages, the conda packages in `/opt/eemt/env`, and the Go modules of `/usr/bin/pebble` from the base image. |
| `env-conda-workflow` | conda | `docker/workflow/conda-lock.yml` | The same conda set as `image-eemt`, taken from the lock. |
| `image-eemt-web` | image | `eemt-web:<VERSION>` (`docker/web-interface/Dockerfile`), scanned by syft | Debian 13 deb packages, the PyPI packages, the Python interpreter of the base image, and the Docker CLI binary. |
| `env-pip-web` | pip | `web-interface/requirements.txt` | The hashed web interface lock. |
| `env-conda-notebooks` | conda | `notebooks/conda-lock.yml` | The notebook environment. |
| `env-conda-notebooks-minimal` | conda | `notebooks/minimal-conda-lock.yml` | The minimal notebook environment. |
| `env-pip-docs` | pip | `requirements-docs.txt` | The documentation toolchain. |
| `env-pip-dev` | pip | `requirements-dev.txt` | The test, lint and SBOM tools. |
| `cargo-rsun` | cargo | `rsun/Cargo.lock` and `cargo metadata` | Every crate in the rsun workspace. |
| `lean-eemtverify` | lean | `lean4-verification/lake-manifest.json` | The Lean toolchain and Lake packages. This target is generated only once the manifest is tracked; it is not tracked yet (finding F-A-031). |

Two more files sit next to them:

- `manifest.json`: for each target, its kind, both files with their sha256 and spec version, its inputs (the lock first) with their sha256, the producing tools with their versions and image digests, and its component count. It also lists every tracked lock file with its sha256, the targets made from it, or the reason it has none.
- `SOURCE_DATE_EPOCH`: one integer, the time written into every document. It is committed so that rebasing or regenerating does not change the documents. Change it only on purpose, for example to the commit date of a lock refresh.

The target table lives in `scripts/sbom/targets.toml`. Component counts are in `manifest.json` and are computed there, not written by hand.

## Regenerate

```bash
scripts/sbom/generate.sh                 # build both images, then regenerate everything
scripts/sbom/generate.sh all --no-build  # use existing eemt:<VERSION> and eemt-web:<VERSION>
scripts/sbom/generate.sh static          # only the documents made from lock files
scripts/sbom/generate.sh aggregate       # only eemt.* and manifest.json
scripts/sbom/validate.sh                 # every gate below
scripts/sbom/vuln-report.sh              # grype report in build/sbom-vuln/ (not a gate)
```

`EEMT_SBOM_IMAGE_PREFIX=eemt-work/` makes the scripts build and scan `eemt-work/eemt:<VERSION>` instead of `eemt:<VERSION>`. `EEMT_SBOM_CACHE=<dir>` keeps the Python tool venv and the cargo registry between runs.

Every tool runs in a container pinned by digest. The digests are in `scripts/sbom/lib.sh`, and `scripts/locks/refresh.sh images` re-resolves their tags:

| Tool | Where it runs |
|---|---|
| syft | `anchore/syft` |
| cyclonedx-py, cyclonedx-python-lib, spdx-tools (pyspdxtools), ntia-conformance-checker, PyYAML, pytest | The pinned `python:3.14.10-slim-trixie` image, from the hashed `requirements-dev.txt` |
| `cargo metadata` | `rust:1.100.0-slim` |
| grype | `anchore/grype` |

Network access is needed only for these:

- the first installation of the Python tools
- `cargo metadata`, which downloads the crates to read their licences
- the grype database

If you change a lock input (an `environment.yml`, a `requirements*.in` or `Cargo.toml`), do these in the same branch:

1. Run `scripts/locks/refresh.sh`.
2. Run `scripts/sbom/generate.sh`.
3. Commit the changed `sbom/` files.

`validate.sh` fails if a lock file no longer matches the sha256 recorded in `manifest.json`.

## How the documents are produced

- **Images.** syft 1.57.1 scans a `docker save` tarball with `--select-catalogers +conda-meta-cataloger`, which makes the conda packages visible. File metadata is off. The SPDX file comes directly from syft and is not converted from CycloneDX.
- **Conda locks.** `scripts/sbom/lock2cdx.py conda` writes one component per package of the `linux-64` platform. Each has a `pkg:conda` purl with build, channel, subdir and type, SHA-256 and MD5 from the lock, the download URL, and dependency edges. Pip entries of a conda lock become `pkg:pypi` components. Licences are covered further down.
- **Pip locks.** `cyclonedx-py requirements --sv 1.7 --output-reproducible` runs on the hashed lock. The sha256 values the lock allows for each release (wheels and sdist) are recorded on the distribution reference. They are not a component hash, because the lock allows several files per release.
- **Cargo.** `lock2cdx.py cargo` reads `Cargo.lock` for every package, the checksum and the dependency edges. Licences come from `cargo metadata --locked --all-features`, run in the pinned Rust image. The legacy `MIT/Apache-2.0` form is read as `MIT OR Apache-2.0`. The workspace crates have no purl, and their supplier is the project.
- **SPDX twins of lock-derived documents.** `scripts/sbom/cdx2spdx.py` converts the CycloneDX file. `syft convert` was tried on `env-conda-workflow`, `env-pip-web` and `cargo-rsun` and lost every package checksum, supplier and download location. It also added the root as an extra package. `cdx2spdx.py` keeps all of them.

## Normalisation (`scripts/sbom/normalize.py`)

Every document goes through `normalize.py`, which uses the standard library only. Applying it twice gives the same bytes.

- **Timestamps and identifiers.** Timestamps come from `SOURCE_DATE_EPOCH`. The CycloneDX `serialNumber` and the SPDX `documentNamespace` are uuid5 values computed from the canonical content, so they change only when the content changes.
- **Removed data:**
  - file components and files
  - image layer ids
  - syft's per-run `package-id` purl qualifier
  - all image labels (one carries an e-mail address)
  - the image id and digest
  - the scanned tarball path
- **Conda packages in an image.** These get their `pkg:conda` purl, SHA-256, MD5 and download URL from the image's own conda-meta records, read from the syft-json output of the same scan.
- **Duplicates.** A component whose every file belongs to one conda package is merged into that package and recorded on it: in CycloneDX as property `eemt:merged-duplicate`, in SPDX as a comment. These are the python dist-info entries, the binaries syft recognises, and the launchers pip and setuptools vendor. The `python` binary match spans the conda packages `python` and `libpython`, so it is merged into `python`. Dependency edges of merged components are dropped rather than moved: syft attaches a Python requirement to one of several same-named dists at random (for example `tomli` in site-packages and in `setuptools/_vendor`), which made two scans of one image differ. Conda packages get their edges from their own conda-meta `depends` instead.
- **Operating system.** syft writes the image's operating system as a CycloneDX component but not as an SPDX package. It is added to SPDX from the same scan, so both files list the same components.
- **Stable references.** `bom-ref` values and SPDXIDs are rebuilt from the purl, or from type, name and version. Components with the same name and version are told apart by a hash of their file locations. Every reference is rewritten to match.
- **Licence references.** Every `LicenseRef-` used in SPDX is declared in `hasExtractedLicensingInfos`.
- **Formatting.** Keys and arrays are sorted, with a two-space indent and a trailing newline.

## Suppliers

The supplier is whoever distributes the component. It is never the EEMT project, except for the project's own components: the document roots and the rsun workspace crates.

| Component | Supplier |
|---|---|
| conda packages | conda-forge |
| deb packages and OS in `image-eemt` | Ubuntu (Canonical Ltd.) |
| deb packages and OS in `image-eemt-web` | Debian |
| `pkg:pypi` | Python Package Index (PyPI). syft's author-as-supplier moves to `originator`. |
| `pkg:cargo` | crates.io |
| Lake packages | the GitHub owner of the repository |
| Components with no package manager | a per-target path rule in `targets.toml`, listed below |

The path rules for components with no package manager:

- `/usr/bin/pebble`: Canonical, from the ubuntu base image
- `/usr/local/bin/docker`: Docker Inc., from the docker CLI image
- pip's vendored launchers: PyPI
- the interpreter in `/usr/local`: Docker Official Images, from the python base image

## Licences

- **Root components.** The images, the environments and the release aggregate `eemt` bundle third-party software under many licences (GRASS GPL-2.0-or-later, CCTools GPL-2.0-only, GEOS LGPL-2.1-only, ...). Their root component therefore declares no licence: no `licenses` in CycloneDX, `licenseDeclared: NOASSERTION` in SPDX. Only roots that are the project's own code declare one: `cargo-rsun` (`rsun`, GPL-2.0-or-later) and, once generated, `lean-eemtverify` (BSD-3-Clause). The `root_license` key in `scripts/sbom/targets.toml` sets this.
- **Images.** Licences are those found in the image: conda-meta for conda packages, the copyright files of the deb packages, and the metadata of the Python packages.
- **`env-conda-workflow`.** It has the same licences as the image's conda packages, because both are the same builds (identical purls).
- **The notebook environments.** conda-lock files carry no licences. A notebook package gets a licence only when the workflow image contains the identical build. `manifest.json` gives the number of components per document. Count the components that have licences directly from each document.
- **Pip documents.** These have no licences, because `cyclonedx-py requirements` does not read them.
- **`cargo-rsun`.** Every crate has a licence except `rsun-cli`, which declares none (finding F-A-001).
- **Docker CLI.** The Go modules of the Docker CLI binary have no licence and an `UNKNOWN` version in syft's output. The binary is Apache-2.0, but its licence text is not shipped in the image.

## What `scripts/sbom/validate.sh` checks

All of these checks are gating:

1. **CycloneDX schema.** Every `*.cdx.json` is CycloneDX 1.7 and passes the strict 1.7 JSON schema (cyclonedx-python-lib).
2. **SPDX validation.** Every `*.spdx.json` passes `pyspdxtools`.
3. **NTIA minimum elements.** Every SPDX document passes `ntia-conformance-checker`. No document is exempt (`NTIA_NONBLOCKING` in `validate.sh` is empty).
4. **Cross-checks** (`scripts/sbom/crosscheck.py`):
   - The conda packages in `image-eemt` and `env-conda-workflow` equal `docker/workflow/conda-lock.yml` by name, version, build and sha256.
   - The PyPI packages in `image-eemt-web` equal the pins of `web-interface/requirements.txt`. The only exception is `pip`, which the base image ships.
   - `manifest.json` lists every tracked lock file with its current sha256.
   - The recorded hashes, inputs, counts, spec versions and tool versions are current.
   - Each CycloneDX/SPDX pair lists the same components.
   - The aggregate matches its members.
   - No image label, image id, scan path, home directory, user name or host name appears in any document.
5. **Secret scan.** `scripts/sbom/secret_scan.py` reads `docker export` of both images and fails on any of these:
   - the Work Queue password file or any `*.password`
   - `.netrc`, `.git-credentials`, `.pypirc`, `.docker/config.json` or `.env`
   - SSH private key files
   - `jobs.db` or SQLite files
   - any file under `uploads/` or `results/`
   - PEM private key blocks

   `--skip-image-scan` skips this step and says so.

The vulnerability report is not a gate. `scripts/sbom/vuln-report.sh` runs grype on the two image SBOMs and writes to `build/sbom-vuln/`, never under `sbom/`. Its results change whenever the vulnerability database is republished. Blocking vulnerability checks on the lock files are a separate requirement: pip-audit and cargo audit in `scripts/locks/check.sh`.

## Drift

Running `generate.sh all` twice leaves `git diff -- sbom/` empty. CI can therefore gate on that diff after regenerating.

On 2026-11-15, both images were rebuilt with `docker build --no-cache` from the same commit. The rebuilt images had new image ids, but the regenerated, normalised documents were byte-identical to those of the original images. The image documents still depend on more than the lock files:

- the base images, pinned by digest
- the Docker CLI image, pinned by digest
- the files the Dockerfiles copy

A change to any of these changes `image-*.json`, even when no lock changed. A rebuild on a later date, after the base image tags have moved, was not tested. The digest pins should keep such a rebuild identical, because the build itself installs nothing unpinned.
